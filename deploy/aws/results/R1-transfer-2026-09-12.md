# R1 · bucket ↔ executor transfer, AWS half (2026-09-12)

Question (decision "remote session storage", risk R1): how fast can a Lambda MicroVM pull a 1 GiB
object out of S3 and push one back? Every cold-start estimate in the decision is a multiple of it.
Thresholds from the decision: **pass ≥ 50 MB/s sustained** (Mend cold pickup ≤ 40 s), **fail < 20
MB/s**.

**Verdict: PASS, with margin.** Single-stream GET 89–100 MB/s, single-stream PUT 115 MB/s, eight
parallel range GETs 780 MB/s. A 1 GiB pickup is 11 s on one connection and 1.4 s on eight. The
egress path (VPC connector + S3 gateway endpoint vs. the service's default public egress) makes no
difference worth designing around.

## Setup

- Account 954648881795, eu-central-1a. `deploy/aws/tofu` applied with `enable_fsx = false` (new
  variable; FSx file system, volume and security group get `count = 0`): VPC, public + private
  subnet, IGW, NAT, S3 gateway endpoint on the private route table, IAM (unchanged from slice 0:
  execution role is logs-only), VPC egress connector, artifacts bucket (public access blocked), ECR,
  log group, budget. 24 resources.
- Bench image `mend-poc-bench` rebuilt from `microvm-bench/` (al2023 arm64 + nfs-utils + git +
  node + curl-minimal), `minimumMemoryInMiB: 4096`, ARM_64, `additionalOsCapabilities: ALL`. Image
  version 2.0 (1.0 failed: `coreutils` conflicts with the base's `coreutils-single`).
- Object: 1 GiB of `/dev/urandom` (sha256 `bc9db036…f256`), uploaded once from this machine (21.6 s,
  ~50 MB/s up) to `s3://mend-poc-artifacts-…/r1/blob-1g.bin`. GET and PUT presigned for 30 min with
  `scripts/presign.py` (boto3, SigV4, regional virtual-hosted endpoint; the global endpoint answers
  a minutes-old bucket with 307, which breaks a curl PUT). **No AWS credentials entered the VM**;
  the URLs arrive over the token-scoped endpoint (`POST /transfer`), never in the run payload.
- VM: `run-microvm` with the `probe` payload (no NFS mount), idle policy 15 min, max 1 h,
  `ALL_INGRESS`. Two configurations, two runs each, sequential (no contention):
  - **connector** — `--egress-network-connectors <vpc-egress>`: traffic leaves through an ENI in the
    private subnet; S3 matches the gateway-endpoint prefix list, everything else goes to NAT.
  - **default** — no egress connector: the service's own public egress (docs: "by default, MicroVMs
    have public internet access").
- Inside the VM: `curl -o /tmp/blob` (single stream, twice), 8 parallel `curl -r` range GETs,
  `curl -T /tmp/blob` PUT, `dd` 1 GiB zeros with fsync, `cp` of the blob, `cat > /dev/null` after
  `drop_caches`, `sha256sum`, and the system facts below. Script: `microvm-bench/bench-transfer.sh`;
  driver: `scripts/09-run-transfer.sh <connector|default>`; raw JSON per run in this directory
  (gitignored), logs `transfer-*.log`.

## Numbers

Rates are decimal MB/s from curl's `speed_download` / `speed_upload` (bytes/s ÷ 10⁶) over the whole
1 073 741 824-byte transfer, i.e. sustained, not peak. Boot is wall time from the `run-microvm` call
to state RUNNING, and to the first `/health` answer through the endpoint.

| run | egress    | boot → RUNNING | → healthy | GET 1 stream       | GET 1 stream (2nd) | GET ×8 ranges     | PUT 1 stream       | TTFB   |
| --- | --------- | -------------- | --------- | ------------------ | ------------------ | ----------------- | ------------------ | ------ |
| 1   | connector | 2.45 s         | 3.10 s    | 92.4 MB/s · 11.6 s | 99.8 MB/s · 10.8 s | 785 MB/s · 1.37 s | 115.6 MB/s · 9.3 s | 97 ms  |
| 2   | connector | 2.58 s         | 3.26 s    | 88.8 MB/s · 12.1 s | 99.8 MB/s · 10.8 s | 778 MB/s · 1.38 s | 115.5 MB/s · 9.3 s | 102 ms |
| 3   | default   | 2.46 s         | 3.10 s    | 99.9 MB/s · 10.8 s | 99.9 MB/s · 10.8 s | 790 MB/s · 1.36 s | 115.5 MB/s · 9.3 s | 66 ms  |
| 4   | default   | 2.49 s         | 3.16 s    | 99.9 MB/s · 10.8 s | 99.9 MB/s · 10.8 s | 787 MB/s · 1.37 s | 115.6 MB/s · 9.3 s | 55 ms  |

Every PUT landed as a 1 073 741 824-byte object (verified with `head-object`, then deleted); every
GET produced the right sha256.

Local disk ceiling (the VM's `/dev/vdc`, ext4, 16 GiB, `/tmp` on it), same four VMs:

| measure                                   | run 1    | run 2    | run 3    | run 4    |
| ----------------------------------------- | -------- | -------- | -------- | -------- |
| `dd` 1 GiB zeros, `conv=fsync`            | 370 MB/s | 304 MB/s | 367 MB/s | 368 MB/s |
| `cp` of the 1 GiB blob (read+write, sync) | 373 MB/s | 307 MB/s | 370 MB/s | 375 MB/s |
| `cat` after `echo 3 > drop_caches`        | 4.3 GB/s | 3.0 GB/s | 6.0 GB/s | 6.0 GB/s |
| `sha256sum` 1 GiB                         | 348 MB/s | 308 MB/s | 348 MB/s | 348 MB/s |

The disk write ceiling is ~300–370 MB/s. The "cold" read is not cold: `drop_caches` returns 0 but
the virtio disk still serves the just-written file at page-cache speed (host-side cache), so the
read ceiling is unmeasured and at least the copy rate. Practical reading: a single S3 stream is
~3.5× slower than the local disk, eight streams are 2× faster than the disk can absorb — a
multi-connection fetch is disk-bound, not network-bound, on this VM.

System facts (identical on all four VMs):

- `uname -m` aarch64, kernel 6.1.166-24.303.amzn2023; **`nproc` 8, `free -m` 16 052 MiB** total / 15
  674 available. The image is created with a 4 GiB baseline; the guest sees the 16 GB / 8 vCPU burst
  ceiling. Billing baseline and guest-visible size are different numbers.
- `df -h /tmp`: `/dev/vdc` ext4 16 G, 15 G available (same device as `/`).
- `fs.inotify.max_user_watches` 126 726 by default; **`sysctl -w …=524288` succeeds** (verified
  after: 524 288). `max_user_instances` 128. Watcher-based capture is possible on this executor.
- `aws` cli: not in the image, deliberately (see below). curl 8.17.0, OpenSSL 3.5.5, HTTP/1.1 to S3.

## Configuration differences

- **Connector**: `checkip.amazonaws.com` reports the NAT gateway's EIP (52.59.164.255), so non-S3
  traffic does go ENI → NAT. S3 answered from public S3 addresses (3.5.x.x) in both configurations;
  that is how gateway endpoints work (route via prefix list, public IPs), so the path cannot be told
  apart from inside the VM. Throughput is the same either way; the connector's only visible cost is
  ~10 MB/s and ~40 ms TTFB on the first single-stream GET (88–92 vs 100 MB/s), which vanished on the
  second GET.
- **Default egress**: a different public IP per VM (18.198.13.229, 3.68.153.215), Lambda service
  address space. Same rates. Billing for this path: S3 → MicroVM within eu-central-1 should be
  in-region service traffic (free), but the MicroVM docs do not say so; worst case it is billed as
  internet egress at $0.09/GB, which for these 6 GiB is ≤ $0.54. Check Cost Explorer in 48 h under
  `environment=aws-microvm-poc` before relying on the default path for bulk transfer.
- Single-stream rate is capped near 100 MB/s on both paths, which looks like a per-flow limit (S3
  per-connection or the VM's virtio-net per-queue), not a VM egress cap: eight flows reach 780 MB/s
  (~6.3 Gbit/s). The documented 8 MB/s at 4 GB applies to the inbound endpoint only and is
  irrelevant to bucket traffic.

## What was not measured, and why

- **`aws s3 cp` inside the VM**: skipped. The execution role grants logs only and the rules say
  never widen IAM; `aws s3 cp` needs credentials for the bucket, so it cannot run without giving the
  VM (hostile by design) S3 access. The eight-range parallel GET is what the cli would do
  (multipart, 8 MiB parts, 10 concurrent by default), so the cli-equivalent number is the ×8 row.
  Adding the cli is cheap on arm64 (`dnf install awscli-2` on AL2023) if a later slice wants it.
- **Multipart PUT**: single stream only. 115 MB/s already clears the bar; a presigned `UploadPart`
  set would need `create-multipart-upload` + N presigned parts + complete.
- **S3 Express One Zone**: not needed; the fail branch that evaluates it did not trigger.
